## 2. 回放方法与统一规则

所有策略共用同一个回放引擎（`tools/simulate_plans.js` 的 `replayOrder`），保证“同一把尺子”：

1. **08:30 从园区中心出发**（`catalog.park.center`），到达项目后立即排队；
2. **等待时间**：取该天 history 中**到达时刻最近的一条快照**里该项目的实测 `wait`（快照间隔约 5–7 分钟，最近快照误差 ≤ 约 3 分钟）；
3. **不可玩即跳过**：该项目在快照的 `closed` 列表里 → `reason='closed'`；快照里没有该项目 → `'missing'`；catalog 里没有该 id → `'invalid'`；
4. **体验时长** = `catalog.durationMin`（缺失按 5 分钟）；**步行** = `planner.walkMinutesBetween`（haversine × 1.35 ÷ 75m/min，四舍五入、最小 1 分钟）；
5. **时间约束**：排队入场（到达）≤ **21:00**；玩完（离开）≤ **21:30**；超时的项目跳过并终止后续（到达时刻单调递增）；
6. **定序一次、不回改**：B/C 在开始前用各自的贪心规则定好顺序，回放过程中**不再重排**（与 D 的静态最优对比）；A 直接用 highlights 原顺序；D 用 `planMustDo` 规划出的顺序。

### 2.1 四种策略

| 策略 | 规则 | 是否使用等待信息 |
| --- | --- | --- |
| **A 地图顺序** | `catalog.highlights` 原顺序 | 否 |
| **B 贪心最近** | 每次从当前位置选**步行最近**的未玩项目（并列取 id 字典序） | 否 |
| **C 贪心最短排队** | 每步在当前时刻、按当天实测排队选**最短**（并列取更近，再取 id） | 是（当天完整实测 = 预知未来，上限参考） |
| **D 精确枚举** | `planMustDo({mode:'max', now:当天08:30, dayType:真实星期})`，用 14 天小时曲线枚举全部顺序取最优 | 是（仅历史曲线，线上可部署） |

### 2.2 指标定义

- **完成数**：8 大必玩中在 21:30 前玩完的数量；
- **平均总排队 / 平均总步行**：14 天日均值；
- **结束时刻**：当天最后一项的离开时刻；一天什么都没玩成按 08:30 计（本仿真 14 天均至少完成 7 项，不受此约定影响）；
- **全完成天数**：完成数 = 8 的天数。

## 5. 分析与结论

### 5.1 为什么完成数差距很小

14 天中有 11–13 天四种策略都能玩完全部 8 项——乐园在 08:30 出发、21:30 闭园的窗口下，8 大必玩的总耗时（排队 + 体验 + 步行）通常只有 9–11 小时，本身是**可完成的**。因此“完成数”存在明显天花板，差异只在少数“高排队/数据中断/临时关闭”的日子出现：

- 10-05：A 的固定顺序把行程拖过 21:00，最后的小飞侠被标 `late`（7 项）；D/B/C 提前消化高排队项目，完成 8 项；
- 10-06：A 最后的小飞侠同样超时、B 最后段的创极速光轮在 21:00 后到达（各 7 项）；D/C 完成 8 项；
- 10-14：B 下午到达 TRON 时项目临时关闭被跳（7 项），C 的动态贪心只排出 7 项就耗尽时间（无跳过）；D 完成 8 项。

即：**D 的优势不是“每天多玩”，而是“在坏日子里更不容易掉项”**（全完成 13/14 天，与 C 并列最高；A 只有 11 天）。

### 5.2 D 的核心优势：结束时刻与总耗时

D 平均 16:54 结束，比 A 早近 1 小时、比 B 早 26 分钟。原因是枚举把“项目间步行 + 各时段排队”联合起来优化，而 B 只看距离（步行 31 分钟最短，但排队 460.7 分钟）、A 完全按地图顺序。D 的步行（41.2）虽比 B 多 10 分钟，但省下 36 分钟排队，净赚 26 分钟。

**10-10 的例外（D 只有 7 项）**：D 规划的顺序在到达 TRON 时，最近快照把 TRON 标为 `closed`（临时停运），回放规则要求跳过且不重排，于是丢了一项（A 也在 08:40 撞上同一段停运；B 15:51、C 13:36 到达时 TRON 已恢复）。这暴露了“静态定序”的真实风险：**线上应在检测到临时关闭/排队突变时触发重规划**，而不是死守出发前的顺序——这也是后续迭代的第一优先级（见 §6）。

### 5.3 为什么 C 的排队最少，但不能算“更好”

C 每次按“当前时刻”的**当天实测排队**选最短——回放里这等于提前知道了未来每个时刻的真实排队。它自然能压低排队（409.3 分钟），但代价是顺序碎片化：步行 63.4 分钟（比 D 多 22 分钟）、结束只比 D 早 6.8 分钟。C 在这里的作用是**理论上限参考**：即便拥有“预知未来”的能力，也只比 D 早结束 7 分钟，说明 D 用历史曲线已经逼近了该信息条件下的最优。

### 5.4 结论

1. **对游客可感知的指标（结束时刻/总耗时），D 明显优于 A、B**：早 57 / 26 分钟结束，少排 50 / 36 分钟；完成数不低于 A，与 B 持平。
2. **C 是上限参考，不是可部署策略**；D 在“只依赖历史曲线”的前提下达到 13/14 天全完成、平均 16:54 结束，是当前可上线的最优选择。
3. **下一步收益最大的不是继续调优顺序，而是“运行中重规划”**：处理临时关闭（如 10-10 TRON）、排队突变、游客实际进度落后于计划。

## 6. 局限与后续改进

| 局限 | 说明 / 改进方向 |
| --- | --- |
| 历史从 09:00 左右开始 | 08:30 出发的项目用最近快照（约 09:00）估计，早高峰排队可能被低估；可补采集 08:00–09:00 数据 |
| 临时关闭只能跳过 | 不重排；线上加“检测 closed/排队突变 → 重跑 planMustDo”即可显著改善（10-10 案例） |
| D 用 14 天曲线含回放日 | 生产 `hourly-stats.json` 本身就是滚动 14 天，属于真实部署条件；若做严格前向验证需用“前一天以前”的曲线 |
| 回放粒度约 5–7 分钟 | 最近快照与真实到达时刻最多差 3–4 分钟；对完成数影响极小 |
| 体验时长取 `durationMin` | 不含排队区内的步行/预演；与实际“项目总占用”可能有偏差 |
| 仅 8 大必玩、14 天、单园区 | 结论方向可推广，绝对数字不宜外推 |
| 未考虑餐饮/演出/休息/尊享卡 | 真实行程会插入这些活动，冲刺计划应作为“骨架”而非完整行程 |
